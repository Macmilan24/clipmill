**Remaining findings**

1. **P1 — Head trimming can delete a valid crop and make the clip unrenderable.** `retime_crop_path` discards every keyframe preceding the new in-point, without preserving the crop evaluated at that boundary. A perfectly valid static crop is commonly represented by one keyframe at time zero. Advancing the head removes that only keyframe while leaving the segment in `speaker_fill`. My probe began with the existing export fixture, applied a word-boundary head trim, and obtained zero crop keyframes; render compilation returned `SpeakerFillWithoutCropPath("seg_1")`. The preview meanwhile treats the absent crop as fit. Preserve an evaluated crop at the new boundary, retain the interior path, and preserve the evaluated tail where needed. Test static crops and interpolated paths through trim, undo/redo, and actual render. Sources: [crop retiming](/Users/sami/Personal/YT/clipmill/crates/clipmill-edit-ir/src/document.rs:715), [render failure](/Users/sami/Personal/YT/clipmill/crates/clipmill-render/src/graph.rs:313). The successful gate used `layout: fit`, so it did not exercise this failure.

2. **P2 — Trim retiming changes the retained audio gain curve.** The splice removes automation points inside the deleted region, but does not insert the gain evaluated at the retained boundary. For a linear 0 dB at 0s → 6 dB at 3s ramp, cutting the first second should leave 2 dB at the new start, increasing to 6 dB at 2s. The probe instead left only a 6 dB point at 2s. The renderer holds the first point backwards, so the retained audio begins at 6 dB. Tail cuts can likewise discard the point that defines an interpolation. Evaluate and preserve the boundary values before splicing. The current test explicitly expects deletion of the first point; that checks the point list, not preservation of the audible envelope. Sources: [automation deletion](/Users/sami/Personal/YT/clipmill/crates/clipmill-edit-ir/src/document.rs:668), [renderer interpolation/hold](/Users/sami/Personal/YT/clipmill/crates/clipmill-render/src/graph.rs:394), [current test](/Users/sami/Personal/YT/clipmill/crates/clipmill-edit-ir/tests/captions.rs:237).

3. **P1 — The proposed manual workaround for short caption fragments cannot fix the track blocking export.** I started from the export crate's passing fixture, added its second presentation, and trimmed at the start of the final word of its first reading cue. Before the trim there were no blocking findings; afterwards export was blocked by `captions.too_brief`. Executing the caption panel's merge operation on the burned-in presentation left the reading cues unchanged and the same export blocker in place. The panel only exposes `plan.cues` and sends grouping commands to `plan.presentation`, normally `burn_in`; export imposes the blocking accessibility checks on `captions.cues`. Automatic polished reflow can reasonably belong to Milestone 3, but a Milestone 1 trim needs a usable route back to export. Either repair reading-cue timing/grouping during the trim or expose an actual reading-track repair control with adequate timing support. Sources: [panel merge](/Users/sami/Personal/YT/clipmill/apps/desktop/src/editor/Captions.tsx:69), [blocking sidecar validation](/Users/sami/Personal/YT/clipmill/crates/clipmill-export/src/validate.rs:202). The gate specifically trims whole reading cues, avoiding this case.

4. **P2 — Export job tracking does not survive leaving the screen or restarting the app.** `queued` exists only in `ExportScreen` state and starts as null on mount. There is no persisted export-job identity or query that restores the document's export. A focused test queued a running export, observed its real-shaped progress state, unmounted the screen, then reopened the same clip with the same API/job data; the delivery panel was gone. The daemon job may continue, but this screen no longer follows it or presents its completed files. Persist the submitted job/snapshot/destination identity or resolve the explicit export from durable daemon state when opening the clip. Reconnect and retry transient delivery-status reads rather than declaring an unknown result permanently settled. Sources: [local export state/reset](/Users/sami/Personal/YT/clipmill/apps/desktop/src/screens/ExportScreen.tsx:72), [delivery watcher](/Users/sami/Personal/YT/clipmill/apps/desktop/src/export/delivery.ts:141), [persisted shell fields](/Users/sami/Personal/YT/clipmill/apps/desktop/src/shell/memory.ts:22). The real gate restarts the daemon before submitting the export; it does not test an app restart during export.

**What the gate establishes, and what its name overstates**

The gate genuinely uses `DaemonClient`, the media protocol, real model workers, document mutations, a daemon restart, rendering, delivery, and decoded-frame checks. It is a valuable integration test.

Its `play_and_scrub` helper requests the first 1,024 bytes and a 4,096-byte range halfway through the MP4. That proves media range serving. It does not invoke the React scrubber, map a selected program time to a browser seek, decode the browser's displayed frame, or verify that playback stops at the clip boundary. See [the byte-range assertions](/Users/sami/Personal/YT/clipmill/apps/desktop/src-tauri/tests/milestone_1.rs:433). React tests over fakes are useful additional evidence but do not close the actual renderer-to-host integration gap. A short real-window acceptance run, or a browser-driven test against the actual host, is still needed for the full UI claim.

The scenario also [trims whole reading cues](/Users/sami/Personal/YT/clipmill/apps/desktop/src-tauri/tests/milestone_1.rs:793) and uses fit layout. It does not cover the remaining crop/gain/fragment failures. It checks corrected text in SRT, VTT, and the ASS track supplied to the encoder; it does not independently recognize that text in decoded pixels. Its decoded samples establish footage timing on synthetic footage, not editorial quality or preview/export visual parity on real interviews.

The disclosed concurrent-analysis failure is a separate known limitation; I did not reproduce that race in this recheck. It should remain an explicit tracked issue, with serialization/deduplication or a clear retry path. It does not explain or excuse the four failures reproduced above. Lack of a merge is a delivery/workflow matter, not evidence that the implementation is wrong.
