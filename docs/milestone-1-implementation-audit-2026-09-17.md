**Milestone 1 implementation audit — 17 September 2026**

The implementation is moving in the right direction, but Milestone 1 is not close to acceptance on the evidence available. The committed identity/approval batch contains useful engineering; the working tree contains an unfinished preview/caption batch. Several original blockers remain, and focused checks exposed additional integration defects. Keep this work and finish it in smaller, demonstrable batches. A rewrite is not warranted.

This audit cannot establish how much effort the implementer spent or whether shortcuts were intentional. It can establish that some comments promise behavior the current code does not deliver, and that component tests do not yet prove the required workflow.

- Approval and document storage now share a database transaction. Repeated direction can return an existing edited document, and an explicit variation can create another. These are substantive fixes, with passing storage tests.

**Findings that block acceptance**

1. **P1 — The selected analysis run stops at the UI boundary.** This gap remains in the committed routing batch. `ResultsLoader` can display a particular run, but approval sends only project/source/candidate; `DirectClipRequest` has no run or manifest reference. The daemon independently loads the latest candidates, ranking, transcript, index, shots, and faces. Opening run A, then approving after run B publishes, can use B's boundaries/transcript or fail because A's candidate is absent. A partially completed reanalysis can also mix stages from different runs. Source identity alone does not fix this. Pass and persist the selected analysis snapshot, resolve its referenced artifacts together, and validate their relationships. Add a real handler-level test with two runs of the same source and a partially published newer run. Sources: [approval request](/Users/sami/Personal/YT/clipmill/apps/desktop/src/results/useResults.ts:205), [request contract](/Users/sami/Personal/YT/clipmill/contracts/proto/clipmill/ipc/v1/daemon.proto:1029), [evidence loader](/Users/sami/Personal/YT/clipmill/crates/clipmilld/src/inspector.rs:82). Confirmed by tracing the request and handler, not by running a full reanalysis.

2. **P1 — A late mutation response can replace the newly opened clip's preview and contaminate its undo history.** In the working tree, `send` increments the request counter _after_ awaiting `applyEditCommand`. If an edit to A is pending, the user opens B, and A's response then arrives, A claims the newest counter and installs its plan while `docId` already names B. `apply` also appends A's inverse to the current undo stack. A focused React hook test reproduced B's identity paired with A's source interval: expected 81,000,000 source ticks, received 54,000,000. Capture a document/session generation before the mutation starts and check it after every await and before updating plan, revision, errors, busy state, or history. Sources: [send](/Users/sami/Personal/YT/clipmill/apps/desktop/src/editor/useEditor.ts:158), [undo-stack update](/Users/sami/Personal/YT/clipmill/apps/desktop/src/editor/useEditor.ts:196).

3. **P1 — Applying a trim does not reconcile the actual media element with the new plan.** In the working tree, initial seeking happens on `loadedmetadata`, while playhead reset depends only on `docId`. A trim changes neither the document ID nor the proxy URL. In a focused component test, changing the clip start from 600s to 605s updated the declared start to 605 but left `video.currentTime` at 600. In another, shortening a 900-frame plan to 300 frames while the playhead was at frame 750 made `segmentAt` return null and removed the video, displaying the missing-proxy message despite a valid proxy. On a plan revision, reconcile/clamp the program playhead, seek through the new mapping, and maintain a truthful playback state. Sources: [playhead lifecycle](/Users/sami/Personal/YT/clipmill/apps/desktop/src/screens/Editor.tsx:103), [metadata-only seek](/Users/sami/Personal/YT/clipmill/apps/desktop/src/screens/Editor.tsx:454).

4. **P2 — The crop transform still uses the wrong element's width.** The new helper computes horizontal translation as a percentage of the source-width video, but `Stage` applies it to the portrait-sized `absolute inset-0` wrapper. CSS percentage translation is relative to the transformed element's box. For landscape footage filling a portrait stage by height, the video is wider than that wrapper, so off-centre crops move too little. Using source dimensions in the helper is insufficient while its transform acts on the stage-sized box. Apply the transform to the correctly sized video element, or calculate stage-space pixel translation explicitly, then compare an off-centre browser crop against a decoded export. Sources: [transform calculation](/Users/sami/Personal/YT/clipmill/apps/desktop/src/editor/player.ts:133), [transformed wrapper](/Users/sami/Personal/YT/clipmill/apps/desktop/src/screens/Editor.tsx:444). This finding is based on CSS geometry and code inspection; no browser/export pixel comparison was run.

5. **P1 — Shared caption correction is scaffolded, not implemented end to end.** The working tree adds word IDs and a `setWordText` command builder. The Rust command enum does not implement `set_word_text`, and a fresh compiled probe rejects it as an unknown variant. The caption UI still calls the old cue/index command and has no arbitrary name-correction input. That old command changes only reading cues: the probe changed the sidecar word to `CORRECTED` while the burned caption remained `the`. With colliding cue IDs it changed a different reading word from the displayed word. The document comment also refers to `assign_word_ids`, but that method/migration is absent. Complete the command, UI correction control, migration, both-presentation propagation, and undo/replay tests together. Sources: [new builder](/Users/sami/Personal/YT/clipmill/apps/desktop/src/editor/commands.ts:60), [current command behavior](/Users/sami/Personal/YT/clipmill/crates/clipmill-edit-ir/src/command.rs:201), [caption UI](/Users/sami/Personal/YT/clipmill/apps/desktop/src/editor/Captions.tsx:210), [migration claim](/Users/sami/Personal/YT/clipmill/crates/clipmill-edit-ir/src/document.rs:98). This is unfinished work, not a regression caused by adding the IDs.

6. **P1 — Backend head/tail retiming is still the original broken implementation.** Fixing the UI's source ticks does not fix the mutation itself. `apply_trim` handles shortening as deletion from the tail even when the head moved, and `splice_program_content` processes reading cues but not burn-in cues. A fresh probe reproduced a one-second remaining segment with a burned cue ending near six seconds; advancing the head by one second also retained the original opening caption. Repair head and tail splices, both caption presentations, gain automation, and reversible crop timing as one operation. Sources: [trim](/Users/sami/Personal/YT/clipmill/crates/clipmill-edit-ir/src/command.rs:308), [splice](/Users/sami/Personal/YT/clipmill/crates/clipmill-edit-ir/src/document.rs:458). This is an unchanged milestone blocker.

7. **P1 — Export still does not bind the user's approval to a revision.** Routing now selects the right document, but `ExportRequestV1` contains no expected revision or approved snapshot address. Planning reads the current document; submission reads it again. A change between those calls can therefore export a revision the user did not review. The backend does correctly snapshot the document it reads at submission, which protects it against later changes; the missing protection is between review and submission. Return an explicit revision/snapshot from planning and require it during submission, rejecting or re-planning on conflict. Sources: [export contract](/Users/sami/Personal/YT/clipmill/contracts/proto/clipmill/ipc/v1/daemon.proto:1239), [planning](/Users/sami/Personal/YT/clipmill/crates/clipmilld/src/service.rs:3165), [submission](/Users/sami/Personal/YT/clipmill/crates/clipmilld/src/service.rs:3233). This is remaining milestone work, confirmed by code inspection.

8. **P2 — Reopening an existing edit unnecessarily depends on rebuilding it from current analysis.** The storage layer can reopen correctly, but the service first loads the latest evidence and calls `assemble`, then asks the store whether a document exists. If a later analysis removes the candidate, or the required evidence cannot be loaded, the valid saved edit cannot be reopened by repeat approval. The storage-only test does not exercise that failure. Resolve the existing identity before requiring fresh evidence, while keeping approval and replay transactional; only a new document/variation should require assembly. Source: [service ordering](/Users/sami/Personal/YT/clipmill/crates/clipmilld/src/service.rs:1523). Present in the committed batch; established by control-flow inspection.

**Recommended handoff**

First finish the identity batch at the service boundary: selected manifest/run, existing-document reopening, and two-run regression tests. Then make preview changes survive trims and asynchronous navigation; verify an off-centre landscape crop. Finish shared caption correction and head/tail retiming together with migration and undo/replay coverage. Finally bind export to the approved revision, wire delivery status and recovery, and demonstrate the agreed exit scenario.

The acceptance demonstration should start in an older project while a newer one exists, use a clip several minutes into a recording, play/scrub, correct a name, trim both ends, undo/redo, restart, export, and decode the actual video plus both caption outputs. Repeat with delayed responses and a newer analysis of the same recording. Green component tests are necessary, but this demonstration is what would justify calling Milestone 1 done.
