# ClipMill 0.3 plan

Scope agreed on 29 September 2026, after 0.2.0 shipped Windows as a beta.

| Area                    | In 0.3                                                                                                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Editorial AI everywhere | The local editorial model on Windows and Linux, through llama.cpp. Macs keep MLX.                                                                                                               |
| Older open bugs         | One recording analysed in two projects at once; whisper's `[BLANK_AUDIO]` fixed where it starts; the development scripts' readiness check.                                                      |
| Studio polish           | Results board hover-scrub, overlap marks and keyboard; the manual clip sheet on the shared player; Models "In use" grouping; Settings export defaults and review preferences; an activity tray. |
| Updates and release     | The app says when a new version is out; the Windows install test runs in CI.                                                                                                                    |

Not in 0.3: the Linux black window on some graphics setups (left as it is);
the Mac app quitting when its window closes (by design); Dependabot, which
now opens one grouped pull request per ecosystem a month (#112).

## 1. Editorial AI on Windows and Linux

Today the editorial component runs only on Apple silicon. On Windows and
Linux clips come from the built-in picker, which judges the shape of a talk
but not what is worth watching. 0.3 brings the same model to both.

### What exists

- `workers/editorial`: `LocalModel` (`runtime.py`) on mlx-vlm 0.7.1. One
  call is `generate(prompt, schema, max_tokens, images)`: greedy decoding
  under a JSON-schema grammar, thinking off, at most 12,000 prompt tokens and
  four 448×448 images, a ten-minute deadline and cancellation at every
  token. The prompts, schemas and parsing live in `inference.py` and
  `metadata.py`, apart from the runtime.
- `runtime_check.py`: one real generation, then `editorial-runtime.json`,
  a receipt naming this machine's hardware fingerprint and the model's
  digest. `selection.rs` admits the editorial worker only against it.
- `models/registry/qwen3-5-editorial-mlx.toml`: Qwen3.5 9B, MLX 4-bit,
  about 6.5 GB. `library.rs` `supported()` refuses any `runtime = "mlx"`
  model off Apple silicon ("Runs only on Macs with Apple silicon.").
- `tools/release/engine.toml`: the `editorial` part lists macOS arm64 only.

### Design

**Runtime: llama.cpp's `llama-server`, pinned.** Each llama.cpp release
publishes a Vulkan build for Windows x64 (33 MB) and Ubuntu x64 (31 MB). It
drives NVIDIA, AMD and Intel graphics through Vulkan, and carries CPU
backends for fifteen processor generations, chosen when it starts, so one
build serves a PC with or without a usable GPU. `bom.toml` pins the archive
by digest, like FFmpeg and uv; `stage.py` stages the server, its libraries
and their licences beside the app on those two platforms. Rejected:
llama-cpp-python (source only on PyPI, while components install
`--only-binary` from hash-pinned locks, and its multimodal support trails
llama.cpp's), the CUDA builds (150 to 600 MB, and Vulkan reaches NVIDIA
cards too) and Ollama (a separate install that cannot be pinned).

**Worker: the same component, a second runtime.** The model's manifest
picks the runtime: `mlx` loads `LocalModel` as today, `llama.cpp` loads a
new `ServerModel` with the same `generate` and `close`. `ServerModel`
starts `llama-server` as its child on loopback, on a free port, with an API
key only the worker holds, the web interface off, one slot, the model's own
chat template (`--jinja`), the vision projector (`--mmproj`) and every
layer on the GPU when one is found. Each call is one streamed
`/v1/chat/completions` request: the schema as `response_format` (llama.cpp
compiles it to a grammar), temperature 0, `enable_thinking: false` through
`chat_template_kwargs`, frames resized to 448×448 as data URLs. Reading the
stream lets cancellation and the deadline close the request, which stops
generation; the 12,000-token check counts the templated prompt with the
server's tokenizer first; token counts come from its `usage`. `close()`
ends the server and its process tree. Prompts, schemas and parsing do not
change, so proposals and reviews keep their contracts.

**Models.** New registry entries, pinned by commit and digest like every
model: Qwen3.5 9B from `unsloth/Qwen3.5-9B-GGUF` (Apache-2.0),
`Qwen3.5-9B-Q4_K_M.gguf` 5.68 GB with `mmproj-F16.gguf` 0.92 GB,
recommended on Windows and Linux; and Qwen3.5 4B (2.74 + 0.67 GB) for
machines the 9B would crowd. `supported()` accepts `runtime = "llama.cpp"`
on Windows x64 and Linux x64. The Add Model sheet's Editorial AI job asks
there for a GGUF repository, the model file and its projector file.

**Proof and admission.** `runtime_check.py` proves a llama.cpp model the
same way and records more: the runtime (`llama.cpp@<build>`), whether it
ran on the GPU or the CPU, and the measured generation speed.
`selection.rs` admits the editorial worker on that receipt. Models shows
the measured speed and, when an analysis would take long on this computer,
says so plainly, and never refuses (the "warn, never cap" rule).

**Engine.** The `editorial` part adds Windows x64 and Linux x64; its
dependencies there add Pillow for the frames and nothing else (HTTP through
the standard library). The daemon hands the worker the server's path as it
hands FFprobe and uv to the engine.

**Security.** The server listens only on 127.0.0.1, answers only the key
its worker made, serves no web page and one request at a time. It loads
only the pinned, hash-checked model files, runs with no console in the
worker's process group and ends with it. Its binaries are pinned by digest.
Licences: llama.cpp (MIT) and LLVM's OpenMP runtime, in the app's notices;
the weights are Apache-2.0.

**Testing.** Unit tests against a fake server (streaming, cancellation, the
deadline, the token limit, schemas). An integration test in CI on Linux
that runs the real server on the CPU with a tiny vision model, so the whole
path runs on every pull request; every schema the worker sends goes
through llama.cpp's grammar converter there. The real 9B runs its proof in
the Windows VM and, before release, on a real PC with a graphics card.

**Risks and open questions.**

- Speed on a CPU alone: a 9B model at 4 bits may generate a few tokens a
  second, so an analysis could take minutes. The proof measures it and the
  4B model is the lighter choice.
- A VM's virtual GPU may offer no Vulkan device, which tests the CPU path.
- MLX and GGUF weights are quantized differently, so replies can differ
  slightly; the evaluation harness can compare them on the corpus.
- Windows on Arm PCs run the x64 build emulated and slowly; a native Arm
  build is later work.

### Phases

1. Pin and stage `llama-server`; `ServerModel` with its tests; the registry
   entries; `supported()`.
2. The proof, admission, speed warning, and the Add Model sheet for GGUF.
3. Trial builds, the VM, a real PC; then the release.

## 2. Older open bugs

- **One recording, two projects.** Analysing the same recording in two
  projects at once fails the second job ("artifact key is already in
  flight"). The second should wait for the artifact the first is producing
  and use it.
- **`[BLANK_AUDIO]`.** whisper.cpp writes non-speech markers as ordinary
  text; the caption deriver drops them. The transcription worker should
  drop them itself. That changes the transcription implementation, so each
  recording is transcribed once more; the changelog says so.
- **Development scripts.** `tools/run-workers.sh` pipes through `rg`,
  which is not a documented dependency, so the editorial readiness check is
  skipped silently. It should use `grep`.

## 3. Studio polish

Left open by the studio review: hover-scrub, overlap marks and keyboard
control on the Results board; the manual clip sheet on the shared player;
grouping by "In use" in Models; export defaults and review preferences in
Settings; an activity tray for work in progress.

## 4. Updates and release

- **A new version is out.** Once a day, and only if the person leaves it
  on, the app asks GitHub for the latest release and, when it is newer,
  says so with a link to its page. It installs nothing; installing updates
  needs signed builds. It counts as a network operation in the Local Lock
  badge, and Settings turns it off.
- **Windows install test in CI.** `.github/workflows/windows-smoke.yml` and
  `tools/drills/packaged_smoke.py` (on `ci/windows-smoke`) install a
  release build on a Windows machine, set it up from the network, run its
  workers and a job, and stop it. It runs by hand against a release run,
  or after one.

## Order of work

Phase 1 of the editorial work, then the open bugs, then updates and
release, then the polish, then editorial phases 2 and 3, and the release.
